# Chain4ensic

> **Multi‑party consensus–based chain of custody for network‑level IoT evidence**\
> *Based on the architecture described by Pezzoni ****et al.**** (Politecnico di Milano)*.

---

## 1. Overview

This repository contains an **end‑to‑end prototype** that demonstrates how a permissioned Ethereum network (PoA clique) can be used to create an auditable, privacy‑preserving **Chain of Custody (CoC)** for network traces harvested at an IoT gateway.

- **Smart‑contracts** (`custom contracts/`) implement evidence registration, Shamir‑sharded key distribution, and on‑chain verification.
- **Docker + Geth** scripts (`geth-Proof-of-Authority-clique/`) spin up a local PoA consortium with boot‑, validator‑ and ordinary nodes.
- **Python helpers** (`geth-Proof-of-Authority-clique/interactions/`) compile, deploy and interact with the contracts.
- **ZoKrates** artefacts (`zero knowledge proof/`) show how Zero‑Knowledge Proofs (ZK‑SNARKs) can be grafted on top of the base protocol for selective evidence disclosure.

By mirroring the bureaucratic checks‑and‑balances of real investigations, the system guarantees that **no single authority can decrypt a piece of evidence**—at least *t*‑out‑of‑*n* key shards must collaborate. fileciteturn0file0

## 3. Deploy smart contracts
1. Import `contracts.sol` into Remix IDE
2. Compile `contracts.sol`
3. Deploy `SmartContractFactory`
4. From the deployed `SmartContractFactory`, call `createSmartContract` function with:
   - `address`: The address that will have verification rights (e.g., the edge server)
   - `proof`: The proof value (if deployed with ZNP active)
5. Check the transaction logs to find the newly created contract address
6. Deploy a new instance by selecting `SmartContractStorage`
7. The UI will expose setter methods and various getters (note: SHA values must be prefixed with '0x')

## 4. Quick‑start (local test‑lab)

```bash
# 1. clone & enter repo
$ git clone https://github.com/your‑fork/iot‑forensic‑blockchain.git && cd iot‑forensic‑blockchain

# 2. bootstrap the PoA clique network
$ cd geth-Proof-of-Authority-clique
$ docker compose -f docker-compose-all-network.yaml up --build -d

# 3. deploy the factory + sample user contract
$ cd interactions
$ python3 deploy.py            # waits 10 s, then saves contract.txt

# 4. append evidence from the Raspberry‑Pi gateway (example)
$ python3 info.py --submit path/to/cipher.bin
```

Dependencies are pinned in `interactions/requirements.txt`; create a fresh **venv** and `pip install -r` to reproduce.

## 5. Evidence life‑cycle

1. **Gateway collects** netflow features & encrypts them with a random AES‑256 key.
2. **IPFS pin**: cipher blob uploaded, CID returned.
3. **Key split**: gateway runs Shamir secret‑sharing (*k=3, n=5* default).
4. **On‑chain tx**: CID hash + key fragments submitted to the personal vault.
5. **Validation**: validator node recomputes CID hash; vault emits `EvidencePushed`.
6. **Retrieval**: >= *k* authorities co‑sign a read request; key is reconstructed off‑chain. fileciteturn0file0

## 7. Security considerations

- **PoA clique** means block signers are known public agencies ➟ easier revocation.
- **Key‑sharding** prevents unilateral evidence decryption.
- **All court‑ordered reads are public** (`EvidenceAccessed` events) to deter fishing expeditions.

See §III‑C of the paper for normative legal analysis under GDPR/LED. fileciteturn0file0
